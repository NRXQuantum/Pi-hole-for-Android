## Pi-hole for Android v3.2.6

This release fixes the failures that appeared after a second **START** or a re-deploy on a device that was already
running Pi-hole:

```
dnsmasq: failed to create listening socket for port 53: Address in use
dropbear ... fail
xrdp ... fail
-bash: line 1: /etc/rc3.d/S04p4a-terminal: No such file or directory
curl: (23) Failure writing output to destination
```

### Root cause: stopped containers kept running

`STOP` only ran the `K` links in `/etc/rc6.d`, and the shipped images do not have `K` links for every daemon.  `dbus`,
`cron`, `syslogd` and others survived every stop.  Worse, when the container had already been unmounted,
`container_stop()` returned "The container is not mounted." and killed **nothing**.  Every later **START** therefore
added another copy of the services:

- the old `pihole-FTL`/`dnsmasq` kept UDP/TCP 53, so the new one reported **Address in use**;
- the old `dropbear` and `xrdp` kept 22/3389, so the new init scripts reported **fail**;
- the old processes kept the previous rootfs files open, so a re-deploy deleted about **1 GB** of data that was still
  referenced.  The space was not reclaimed, the Pi-hole installer ran out of disk, and `curl` aborted with
  **(23) Failure writing output to destination**.

On the affected device 27 orphaned container processes were found (two `pihole-FTL`, two `unbound`, two `xrdp-sesman`,
several `dbus-daemon`/`syslogd`/`cron`).  Terminating them immediately reclaimed about **1 GB** and released every port.

The `S04p4a-terminal` line was a separate race: first-boot provisioning (`android-raspbian`) reorders `rc3.d` links,
so a name captured before the reorder could disappear before it was executed.

### What changed

- **The container is reaped before start, after stop, and before a destructive install.**  Every process whose root is
  either `CHROOT_DIR` or the deployment directory (`TARGET_PATH`) is terminated with `TERM`, then `KILL` after five
  seconds.  This also catches daemons left behind by an unmounted/detached container.  There is now only ever one
  Pi-hole instance.
- **`STOP` works even when the mount is gone.**  It still runs `do_stop` when mounted, but always reaps the container
  afterwards instead of returning early.
- **A deploy stops and unmounts first.**  It no longer extracts over live `proc`/`sys`/`dev` mounts.
- **Deploy checks free space before downloading/extracting.**  It requires 1200 MB for the 32-bit image and 1600 MB for
  the 64-bit image (override with `MIN_FREE_MB`), and fails with a clear message instead of truncating the install.
- **Renamed `rc?.d` entries are skipped** while services are being started/stopped, so the first-boot provisioning can
  reorder them safely.
- **xrdp log ownership is repaired at every start.**  A fresh extraction restores `/var/log/xrdp*.log` as
  `root:root`; xrdp runs as the unprivileged `xrdp` user and aborts with `Could not start log`.  The APK now restores
  `xrdp:xrdp` ownership before starting services.  The image's `android-raspbian` script was also updated so future
  image builds do this themselves.

### Port conflicts with other deployments

Ports are shared with the Android host and with other chroots.  On the test device NetHunter's Kali `sshd` already
listens on port 22, so Pi-hole's Dropbear cannot bind it:

```
tcp 0.0.0.0:22 LISTEN 5018/sshd   # root=/data/local/nhsystem/kali-armhf
```

Stop the other SSH server (or change its port) if you need Pi-hole's Dropbear.  The same applies to 53/3389 when
another DNS/RDP server is running.  This is an environment conflict, not a duplicate Pi-hole instance; v3.2.6 no
longer creates the latter.

### Verification performed

Tested on Samsung SM-J200G (`j2lte`), LineageOS 7.1.2 / SDK 25, ARMv7, MagiskSU 30.7:

| Scenario | Result |
| --- | --- |
| 27 orphaned container processes from earlier starts | all terminated; ports 53/80/443/8080/8443/3389/5353 released |

| New build: `start -m` | one `pihole-FTL`, one `unbound`, one `xrdp-sesman`; DNS answers on 53 |

| APK build | versionCode 320 / versionName 3.2.6, signed with the persistent release key |

### Upgrading

- **From v3.2.1–v3.2.5:** install `pideploy.apk` over the existing app.  The signing certificate is the same, so no
  uninstall is required and existing deployments are kept.  On the first **START** the new build reaps any leftover
  daemons from the previous version and repairs xrdp's log ownership.
- **From the upstream 3.2.0 APK or older:** the signing key differs; uninstall the old Pi Deploy APK once (export your
  Pi-hole configuration with **Teleporter** first), then install this APK.

No re-deploy is required; the disk images are unchanged.
