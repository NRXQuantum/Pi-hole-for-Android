## Pi-hole for Android v3.2.4

This release fixes the deployment failure that survived v3.2.3:

```
/system/bin/sh: <stdin>[4]: /data/user/0/com.desktopecho.pideploy/files/bin/pideploy: not found
```

### Root cause

The app generates `files/bin/pideploy` itself, and the upstream generator writes its first line as:

```
#!/<app files>/bin/sh
```

That `files/bin/sh` is not shipped in the APK.  It is a symlink that only appears when `busybox --install -s` succeeds.
On a device where busybox cannot execute, the symlink is never created, so the kernel rejects every invocation of
`pideploy` with **not found** — even though the file itself exists.  The app then records `files/version` anyway, so it
believes setup succeeded and never retries.

v3.2.3 tried to guard this with an environment check, but the check was placed after the branch that reads an existing
`version` marker.  Since affected devices already had that marker, the check never executed and the error persisted.

### What changed

- **The launcher no longer depends on that symlink.** `pideploy` is now written with `#!/system/bin/sh`.  It locates a
  working busybox (the primary one, then `busybox_arm64`, then `busybox_arm`), repairs `files/bin/sh`, installs the
  applet symlinks, and finally executes the Pi Deploy CLI under busybox `sh`.
- **Both Android ABIs ship inside `bin/all`.**  `busybox_arm64` and `busybox_arm` are extracted with every environment,
  so one extracted environment can recover from an unusable primary busybox on either ABI.
- **The integrity check looks at what can run.**  The environment is considered present only when `pideploy`, a bundled
  busybox and `cli.sh` are available.  The check now runs before `files/version` is consulted.
- **Commands run the launcher through `/system/bin/sh`**, so a stale shebang or a missing execute bit cannot break
  Start either.
- **Initialization still happens without the storage permission**, because extraction only uses internal storage.

### Verification performed for this release

The packaged APK was decoded, its launcher string was extracted from the built DEX, and that exact script was executed
under `/system/bin/sh` on an Android 10 ARM64 device:

| Scenario | Result |
| --- | --- |
| Fresh extraction, no `files/bin/sh` | `help`, `status`, `start` reach the CLI |
| Primary busybox replaced by an unexecutable binary | launcher recovers from `busybox_arm64` |
| Both 64-bit busybox copies broken, `busybox_arm` present | launcher recovers from the static 32-bit build |
| No usable busybox at all | clear `cannot execute a bundled busybox` error, exit 127 |
| App-style invocation through `sh` stdin (`<stdin>[4]`) | `start` prints `The container is not mounted.`, not `not found` |

The APK was also checked for the expected version (`3.2.4`, versionCode `318`), the release certificate, zip alignment,
and the two new busybox assets.

### Upgrading

- **From v3.2.1, v3.2.2 or v3.2.3:** install `pideploy.apk` over the existing app.  It uses the same certificate, so no
  uninstall is required and existing deployments are kept.  The version marker differs, so the first start re-extracts
  the helper environment and rewrites `pideploy` with the new launcher.
- **From the upstream 3.2.0 APK or older:** the signing key differs; uninstall the old Pi Deploy APK once (export your
  Pi-hole configuration with **Teleporter** first), then install this APK and create/restore your deployment.
- If Start ever fails again, the app now logs the reason (for example `cannot execute a bundled busybox`) instead of a
  bare `not found`.
