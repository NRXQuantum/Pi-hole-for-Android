## Pi-hole for Android v3.2.7

This release fixes **START doing nothing after the app is closed and reopened**, and makes the **SSH port setting in
the app apply to the SSH server that actually runs inside the image**.

### START appeared to do nothing

After the app process was closed and opened again, tapping **START** showed the confirmation dialog, but the container
was never started and the console stayed empty.  The app process had a worker thread inside:

```
com.desktopecho.pideploy.EnvUtils.setPermissions(EnvUtils.java:108)
com.desktopecho.pideploy.EnvUtils.setPermissions(EnvUtils.java:115)   (repeated)
com.desktopecho.pideploy.EnvUtils.updateEnv(EnvUtils.java:287)
com.desktopecho.pideploy.EnvUtils.cli(EnvUtils.java)
com.desktopecho.pideploy.ExecService.lambda$onHandleWork$0$ExecService(ExecService.java:31)
```

`updateEnv()` ran `setPermissions(getEnvDir())`, a recursive permission pass over the whole application `files`
directory.  That directory contains the **mounted deployment** (`files/raspbian`, a 2 GB ext4 image with `proc`, `sys`
and `dev` mounted inside it), so the pass walked the entire Raspberry Pi root filesystem instead of the few files that
were just extracted.  It did not finish, `start` was never executed, and `setVersion()` was never reached.  Because the
environment still looked incomplete on the next launch, every later **START** repeated the same walk.

v3.2.7 restricts the permission pass to the directories that the APK actually extracts (`bin`, `web`, `config`, `tmp`
and `cli.sh`).  The mounted deployment is no longer touched.

### SSH port

The Raspbian image runs **Dropbear** (`/etc/default/dropbear`), while the profile's `SSH_PORT` value was only passed to
the optional OpenSSH component (`include/extra/ssh`).  Changing the port in the app therefore did not change the port
that answered: Dropbear kept using its own value.

v3.2.7 writes the app's SSH port into the image's `/etc/default/dropbear` before the init scripts run, so Dropbear
listens on the configured port.  When the image provides Dropbear, the OpenSSH component now reports
`skip (Dropbear handles SSH)` instead of starting a second SSH daemon on the same port.

### Verification

Tested on the affected Samsung SM-J200G (LineageOS 7.1.2, Android 7.1) with the existing deployment kept in place:

| Test | Result |
| --- | --- |
| Install over v3.2.6 (`adb install -r`) | succeeded, data and container preserved |
| Environment update to `3.2.7-321` | finished within 5 seconds |
| Force-stop app, reopen, tap START | container started in about 9 seconds, no stuck `updateEnv` thread |
| SSH on the configured port (`SSH_PORT=2223`) | Dropbear listening on `2223`; `ssh -p 2223 android@…` prints `SSH_OK` |
| Second START while running | services reaped and restarted once, Dropbear still on `2223` |
| STOP, then START again | services stop cleanly and return |

### Notes

- **Same signing key** as v3.2.1–v3.2.6, so this installs as an update.  Existing deployments are kept.
- The disk images are unchanged; only the APK changed.
- Ports are shared with Android.  If another SSH server already owns the configured port (for example NetHunter's
  Kali `sshd` on 22), choose a different SSH port in the app settings.  The default remains 22 for new profiles; set it
  to 2222/2223 if port 22 is already in use.
