## Pi-hole for Android v3.2.5

This release fixes the remaining reason a rooted device could still see:

```
/system/bin/sh: <stdin>[4]: /data/user/0/com.desktopecho.pideploy/files/bin/pideploy: not found
```

even after v3.2.4 fixed the launcher itself.

### Root cause: the app could not write its own data directory

Android reuses `/data/user/0/com.desktopecho.pideploy` when an app is reinstalled. On some devices that directory
keeps the **owner UID of the previous installation**.  The new installation then runs under a different UID and cannot
write `files/`:

```
dumpsys package com.desktopecho.pideploy   -> userId=10086
ls -ln /data/data/com.desktopecho.pideploy -> u0_a81 (10081)
```

The app's environment updater (`EnvUtils.updateEnv`) could not create `files/bin`, so extraction failed with `EACCES`
and returned `false`.  Because the failure happened before `files/version` was written, nothing retried it on the next
launch.  `files/bin/pideploy` therefore never existed, and the system reported the same **not found** error.

This is a POSIX ownership problem, not an Android permission or SELinux problem.  Granting storage access and root to
the app cannot fix it; `updateEnv` itself has to repair the directory.

### What changed

- **The updater repairs its storage before extracting.**  If the app data directory, or an existing environment
  directory, is not writable, `updateEnv` now runs

  ```sh
  chown -R <current-uid>:<current-uid> <app data dir>
  ```

  through `su` and then continues with the normal extraction.  The check is a no-op on a healthy installation, so
  first installs and normal updates never invoke root.
- **All v3.2.4 launcher fixes are included.**  `pideploy` still uses `#!/system/bin/sh`, selects a working bundled
  busybox, repairs `files/bin/sh`, and both ARM ABIs still ship in `bin/all`.
- The disk images are unchanged from v3.2.1–v3.2.4 (identical checksums).

### Verification performed for this release

Tested on the affected device before publishing:

- Samsung SM-J200G (`j2lte`), LineageOS 7.1.2 / SDK 25, ARMv7, MagiskSU 30.7, SELinux permissive.
- App UID `10086`; the data directory was deliberately changed to the previous install's UID `10081` and `files/` was
  emptied to reproduce the failure.

| Scenario | Result |
| --- | --- |
| Stale owner `10081`, empty environment, app launched | data directory repaired to `10086` within 4 s |
| Same launch, extraction continues | `files/version` = `3.2.5-319`, `files/bin/pideploy` present within 10 s |
| Relaunch with healthy ownership | version stays `3.2.5-319`; no unnecessary root call |
| `run-as com.desktopecho.pideploy` | works (no more "corrupt installation") |
| `./bin/pideploy status` | reaches the Pi Deploy CLI |
| UI **START** | runs the full `do_start` bootstrap; no `not found` |

The only errors left in the UI log during **START** are the expected ones from not having downloaded a container
image yet (`The container is not mounted.`).

### Upgrading

- **From v3.2.1, v3.2.2, v3.2.3 or v3.2.4:** install `pideploy.apk` over the existing app.  It uses the same
  certificate, so no uninstall is required and existing deployments are kept.  The first launch extracts the updated
  helper environment.  If the data directory is stale, the app repairs its ownership automatically on that launch
  (root is required, as it already is for Pi Deploy).
- **From the upstream 3.2.0 APK or older:** the signing key differs; uninstall the old Pi Deploy APK once (export your
  Pi-hole configuration with **Teleporter** first), then install this APK and create/restore your deployment.
