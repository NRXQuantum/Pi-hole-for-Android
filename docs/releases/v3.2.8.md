## Pi-hole for Android v3.2.8

This release fixes the **SSH on/off switch**: with SSH switched off in the app, starting the container still started
Dropbear on the configured port.

### Why the switch was ignored

The app has two separate SSH paths:

- the optional OpenSSH component (`include/extra/ssh`), which is added to the profile's `INCLUDE` list only when
  `is_ssh` is on; and
- the Raspberry Pi image's own **Dropbear**, which is started by the image's SysV links (`/etc/rc3.d/S03dropbear`)
  during container init.

Turning SSH off removed `extra/ssh` from `INCLUDE`, but nothing told the image's init to skip Dropbear.  The result was
that SSH stayed available even though the app showed it as off.  v3.2.7 fixed only the *port* by writing
`DROPBEAR_PORT` to `/etc/default/dropbear`; the switch itself was still not connected to Dropbear.

### What changed

The app keeps the switch in `shared_prefs/properties_conf.xml`, but it does **not** rewrite the profile's `INCLUDE` list
when the switch is toggled for an existing deployment.  `cli.sh` therefore reads `is_ssh` from that preference file
(falling back to `INCLUDE` only when the file is unavailable), so a stale `INCLUDE` can no longer keep SSH on.

Before the container's init scripts run, `cli.sh` now applies both SSH settings to Dropbear:

- **SSH on** — the app adds `extra/ssh` to `INCLUDE`; Dropbear's `S??dropbear` start links are restored in `rc2.d` …
  `rc5.d` (created if missing), so Dropbear starts on the configured port.  The OpenSSH component still reports
  `skip (Dropbear handles SSH)`.
- **SSH off** — the `S??dropbear` start links are removed before init, so the image's init does not start Dropbear at
  all.  Pi-hole, DNS, the web interface and xrdp start normally.
- The configured **SSH port** continues to be written to `/etc/default/dropbear` whenever it is valid.

The change is applied on every START, so it also works after a previous session, a STOP/START cycle, or a re-deploy.

### Verification

Tested on the same Samsung SM-J200G (LineageOS 7.1.2, Android 7.1) with the existing deployment kept in place:

| Test | Result |
| --- | --- |
| Install over v3.2.7 (`adb install -r`) | succeeded, data and container preserved |
| SSH off (`is_ssh=false`) with a stale profile that still lists `extra/ssh`, tap START | no Dropbear process, no listener on the configured port, `rc*.d/S??dropbear` links absent |
| SSH on, tap START | links restored and Dropbear listening on the configured port (2225) |
| Pi-hole / DNS / web UI / xrdp while SSH off | all start normally |

### Notes

- **Settings take effect on the next START.** If the container is already running, tap STOP then START after changing
  the SSH switch or port.
- **Same signing key** as v3.2.1–v3.2.7, so this installs as an update.  Existing deployments are kept.
- The disk images are unchanged; only the APK changed.
